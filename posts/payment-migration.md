결제 데이터를 모두 옮겼어도, 다음 구독 갱신이 실패한다면 마이그레이션은 끝난 게 아니다.

구독 이벤트는 기존 구독을, 환불은 원래 결제 내역을 찾아야 한다. 담당자와 문서가 부족한 시스템에서 이 연결을 복원하다가, 현재도 중복 구독을 만드는 로직까지 발견했다.

## 옮길 데이터보다 먼저 정해야 했던 것

인수합병에 따른 재무 데이터 통합을 위해 결제 서버를 이전했다. 대상은 약 80만 건의 주문과 800만 건의 결제 관련 데이터였고, 기한은 5월이었다.

새 결제 서버 담당자는 이전 API를 제공했다. 나는 기존 데이터 분석, 식별키 선정, 정합성 검증, 이전 실행과 서비스 연동을 맡았다. 우선순위는 다음과 같이 정했다.

1. **구독 유지:** 활성 구독과 최근 결제를 옮겨 이후 이벤트가 기존 주문에 연결되게 한다.
2. **재무 정합성:** 당해 연도 결제·환불 내역을 이전하고 정산을 맞춘다.
3. **과거 이력 보존:** 나머지 전체 내역을 이전한다.

## 데이터를 맞추다 중복 구독을 발견했다

테이블을 조인해 연결 건수를 비교하고, 금액·상품·사용자·시각을 대조했다. 상품을 찾을 수 없는 일부 결제는 2022년 주문 서버 이전 당시 넘어오지 않은 주문과 관련돼 있었다. 과거 서버와 결제 제공자 사이트를 찾아 보정하고, 복원에 한계가 있던 상품은 `legacy`로 구분했다.

더 큰 문제는 중복 구독이었다. 서비스는 이를 허용하지 않았지만, 갱신 실패를 구독이 없는 상태로 판단하면서 다음 경로가 열려 있었다.

```text
구독 A 갱신 실패 → 새 구독 B 구매 허용
  → 이후 A의 갱신도 성공 → 두 구독이 각각 갱신
```

**이용 권한이 없다는 사실과, 기존 구독이 종료됐다는 사실은 달랐다.** 갱신 실패만으로 구독이 없다고 판단하지 않도록 수정했다.

다만 새 구매만 막으면 사용자는 권한을 회복할 방법도 잃는다. Product Owner에게 갱신 실패를 알리고 구독 관리 페이지로 연결하는 흐름을 요청했다. 과거 중복 내역을 정리하면서, 같은 문제가 다시 생기는 경로도 고쳤다.

## 재시도 전에, 무엇이 같은 결제인지부터 정했다

기존 데이터의 해석과 새 서버의 적재 규칙을 각 팀이 책임지도록 REST API로 이전했다. 재요청의 중복을 막으려면 먼저 **구독 식별자와 개별 결제 식별자를 나눠야 했다.**

```text
구독 S → 3월 결제 P1, 4월 결제 P2
P1 재요청 → 같은 결제 / P2 이전 → 같은 구독의 다른 결제
```

위는 개념 예시다. 구독 키만으로 중복을 판단하면 다음 달 결제도 중복으로 취급할 수 있다. 제공자별로 상품·구독·결제·환불 키를 선정하고, 환불과 원래 결제의 관계도 매핑했다.

## API 성공과 서비스 반영 완료를 나눠 기록했다

API 적재 후에는 서비스 주문에도 새 결제 서버의 식별정보를 저장해야 했다. 이 매핑이 실패하면 데이터가 있어도 이후 이벤트를 연결할 수 없다. 한 건의 처리를 세 종류의 기록으로 남기고 각각 별도 트랜잭션으로 커밋했다.

| 기록 | 확인할 내용 |
| --- | --- |
| 요청 파라미터 | 어떤 원본을 어떤 값으로 이전하려 했는가 |
| API 응답 | 결제 서버에서 어떤 결과를 돌려줬는가 |
| 주문 매핑 | 서비스 주문에 식별정보가 반영됐는가 |

후속 저장이 실패해도 앞 단계의 기록은 남았다. 단, 응답 기록이 없다고 적재 실패를 단정할 수는 없다. 적재 후 응답만 유실됐을 수도 있기 때문이다.

확인이 필요한 건은 수동으로 조사하고, 대상 ID 목록을 지정해 같은 식별키로 재요청했다. **기록은 진행 상태를 확인하는 근거였고, 멱등 API는 재요청의 중복을 막는 장치였다.**

## 전환 중에는 결제를 막고, 권한 만료를 늦췄다

배포 시작부터 예상 종료 시점에 버퍼를 더한 시간까지를 전환 구간으로 잡았다. 이벤트 처리가 지연돼도 기존 사용자의 권한 공백은 막아야 했다.

1. 결제·갱신 처리가 지연될 수 있다는 점과 권한 보호 방침을 미리 공지했다.
2. 신규 결제를 잠시 차단하고, 구간 내 갱신 대상 구독의 권한 만료를 전환 종료 예정 시점까지 미뤘다.
3. 이전 완료 후 지연된 갱신·취소·환불 이벤트를 소급 처리했다.

## 하나의 구독 키를 확정할 수 없었던 19건

App Store 구독 19건은 후보가 여러 개이거나 최초 거래를 판별하기 어려워 키를 하나로 확정할 수 없었다. 임시키로 이전하되, 구독을 찾지 못하는 이벤트는 알림을 받아 확인했다.

1. 실제 갱신 이벤트의 구독 키와 기존 후보를 수동 대조해 키를 확정한다.
2. 이전된 결제 내역을 정확한 키로 보정한다.
3. 연결하지 못했던 이벤트를 재시도한다.

19건 모두 다음 갱신 시점에 보정을 마쳤다. **임시키로 적재한 뒤에도 이벤트 복구까지 작업 범위에 포함했다.**

## 무엇을 확인해야 완료라고 할 수 있을까

전체 데이터를 이전했고, 실제 적재는 약 80만~90만 건의 API 요청 규모였다. 완료 여부는 세 가지로 나눠 확인했다.

| 확인 대상 | 검증 방법 |
| --- | --- |
| 누락·중복 | 결제 서버 측에서 이전 건수와 멱등성 키 대조 |
| 당해 연도 재무 데이터 | 두 서버의 결제·환불 정산 금액 대조 |
| 이후 이벤트 | 양쪽 서버의 실패를 Slack 알림으로 모아 주문 연결과 권한 처리 확인 |

건수와 합계의 일치가 개별 기록의 완전한 일치를 보장하지는 않는다. 금액 대조도 당해 연도에 한정했으므로, 전체 과거 내역까지 같은 수준으로 검증했다고 볼 수는 없다.

## 오류를 줄이자 남은 오류도 보이기 시작했다

중복 구독이 줄면서, 이미 권한이 있는 사용자에게 다른 구독이 다시 권한을 부여하려던 오류도 더 이상 관찰되지 않았다.

반복 오류가 줄자 남은 알림을 살필 수 있었다. 정상 처리를 실패로 잡던 false positive도 정리하면서, 들어오는 결제 실패를 하나씩 확인할 수 있는 수준으로 모니터링을 개선했다. 이 일련의 후속 개선을 합쳐 **결제 처리 오류율은 80% 이상 낮아졌다.**

과거 데이터의 연결을 복원하는 과정에서, 그 연결을 계속 깨뜨리던 로직까지 찾아 고칠 수 있었다.
