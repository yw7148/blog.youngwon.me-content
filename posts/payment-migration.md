결제 데이터를 모두 옮겼어도, 다음 구독 갱신이 실패한다면 마이그레이션은 끝난 게 아니다.

갱신·취소·만료 이벤트는 기존 구독을 찾아야 하고, 환불은 원래 결제 내역과 연결돼야 한다. 이 연결이 끊기면 과거 내역이 온전히 남아 있어도 서비스는 정상적으로 동작하지 않는다.

담당자와 문서가 부족한 상황에서, 중복과 누락 없이 데이터를 옮기고 서비스 중단을 최소화해야 했다. 데이터를 대조하다 보니 서비스가 허용하지 않는 중복 구독도 발견했다. 이전할 데이터의 문제를 따라가는 일이, **기존 결제 로직의 오류를 고치는 작업**으로 이어졌다.

## 옮길 데이터보다 먼저 정해야 했던 것

회사의 인수합병 과정에서 분산된 재무 데이터를 통합하기 위해 결제 서버를 이전하게 됐다. 기존 서비스에는 약 80만 건의 주문이 있었고, 여러 결제 제공자의 웹훅과 결제 관련 테이블에는 약 800만 건의 데이터가 있었다. 이 기록들을 조합해 새로운 결제 서버가 이해할 수 있는 결제·환불 내역으로 만들어야 했다.

새 결제 서버 담당자는 마이그레이션 API를 제공했다. 나는 기존 데이터의 규모와 관계를 파악하고, 식별키 선정과 정합성 확인, 이전 실행과 상태 추적, 서비스의 결제 연동 코드 변경을 맡았다. 기존 결제 서버의 담당자는 부재한 상태였고, 재무 검토 일정에 맞춰 5월까지 완료해야 했다.

범위를 먼저 세 단계로 나눴다. 가장 먼저 지켜야 할 것은 활성 구독의 유지였다. 이를 위해 활성 구독 정보와 최근 결제 내역을 이전하고, 이후 갱신·취소·만료·환불 이벤트가 기존 주문에 연결돼야 했다. 다음은 당해 연도 결제·환불 내역을 이전해 재무 정산을 맞추는 것, 마지막은 전체 과거 내역을 이전하는 것이었다.

이 기준으로 어떤 실패부터 막아야 하는지 정했다. 최종적으로는 전체 데이터를 이전했지만, 조사와 검증의 우선순위는 **현재 구독과 이후 결제에 영향을 주는 연결**에 뒀다.

## 데이터를 맞추다 중복 구독을 발견했다

가장 먼저 한 일은 전체 테이블을 조회하며 관련 테이블과 컬럼을 정리하는 것이었다. 이름이 비슷한 컬럼을 조인해 연결되는 건수를 비교하고, 주문 금액·상품 금액·실제 결제 금액, 상품 ID, 사용자 ID, 발생 시각을 대조했다.

연결되지 않는 기록을 따라가다 과거 서버까지 거슬러 올라가기도 했다. 상품을 찾을 수 없는 일부 결제는 2022년 주문 서버 마이그레이션에서 넘어오지 않은 주문과 관련돼 있었다. 이전 서버와 결제 제공자 사이트를 확인해 정보를 보정하고, 과거 내역임을 구분해야 하는 상품에는 `legacy`를 명시했다.

그런데 누락된 관계를 복원하는 것보다 먼저 원인을 해결해야 할 문제도 나왔다. 서비스는 중복 구독을 허용하지 않았지만, 실제 데이터에는 중복 구독이 여럿 존재했다.

주요 원인은 갱신 결제 실패 후의 처리였다. 서비스는 갱신에 실패하면 유효한 구독이 없다고 판단하고 새 구독을 허용했다. 하지만 기존 구독은 이후 다시 갱신될 수 있었다.

```text
기존 구독 A의 갱신 결제 실패
  → 서비스는 구독이 없다고 판단
  → 사용자가 새 구독 B를 구매
  → 이후 구독 A의 갱신도 성공
  → 두 구독이 함께 유지되며 각각 갱신을 시도
```

핵심은 **지금 이용 권한이 없다는 사실과, 기존 구독이 더 이상 갱신되지 않는다는 사실을 구분하는 것**이었다. 갱신 결제가 실패한 상태를 곧바로 구독이 없는 상태로 취급하지 않도록 로직을 수정했다.

하지만 새 구독 구매만 막으면 또 다른 문제가 생겼다. 사용자는 이용 권한이 없는데, 권한을 얻기 위한 구독 구매도 할 수 없게 된다. 그래서 Product Owner에게 갱신 실패를 앱에서 알리고, 바로 구독 관리 페이지로 이동할 수 있는 흐름을 추가해달라고 요청했다. 사용자가 기존 구독의 문제를 해결할 경로도 필요했기 때문이다.

이미 생긴 중복 데이터는 정리하더라도 이 로직이 그대로라면 다시 쌓일 수 있었다. 이번 이전에서는 과거 내역의 보정과 함께, 같은 불일치를 만드는 경로도 수정했다.

## 재시도 전에, 무엇이 같은 결제인지부터 정했다

적재는 제공받은 REST API로 진행했다. 새 결제 서버 DB에 직접 접근하는 방식도 검토했지만, 기존 데이터의 해석과 새 서버의 적재 규칙을 각 팀이 책임지는 구조에서는 API를 통해 조율하는 편이 적합하다고 판단했다.

API를 쓰기로 했다고 재실행 문제가 해결되는 것은 아니었다. 중간에 실패한 요청을 다시 보낼 때 무엇을 같은 건으로 판단할지 정해야 했다. 내 작업의 핵심도 멱등 API 자체를 구현하는 것보다 **각 결제 제공자의 데이터에서 그 기준을 찾는 일**에 있었다.

구독을 식별하는 키와 개별 결제를 식별하는 키는 목적이 달랐다. 하나의 구독에는 여러 번의 갱신 결제가 쌓인다. 구독 키만으로 결제의 중복을 판단하면 정상적인 다음 달 결제까지 중복으로 취급할 수 있다.

아래는 이 차이를 설명하기 위한 개념 예시다. 실제 결제 제공자의 필드명은 아니다.

```text
구독 S
  ├─ 3월 결제 P1
  └─ 4월 결제 P2

P1의 이전 요청을 다시 보냄 → 같은 결제
P2를 새로 이전함          → 같은 구독의 다른 결제
```

App Store, Google Play, Stripe 등 제공자별로 상품·구독·결제·환불을 구분할 키를 선정하고, 환불이 어느 결제에 속하는지도 매핑했다. 이후 이벤트를 처리할 때도 이 관계가 유지돼야 했다. 새 결제 서버가 구독을 찾는 것과 서비스가 그 구독에 연결된 주문을 찾는 것, 두 연결이 모두 필요했다.

## API 성공과 서비스 반영 완료를 나눠 기록했다

한 건을 이전하는 흐름은 기존 결제 내역 조회, 요청 파라미터 생성, API 호출, 서비스 주문 데이터에 새 결제 서버의 식별정보 저장으로 이어졌다.

새 결제 서버에 적재하는 것으로 작업이 끝나지 않았다. 응답을 받아 우리 쪽 주문에도 필요한 매핑을 저장해야 이후 결제 이벤트를 처리할 수 있었다. 이 단계가 실패하면 결제 서버에는 데이터가 있는데 서비스에서는 연결할 수 없는 상태가 남았다.

이를 추적하기 위해 한 건의 처리에서 다음 세 종류의 기록을 각각 별도 트랜잭션으로 커밋했다.

| 기록 | 확인하려는 내용 |
| --- | --- |
| 요청 파라미터 | 어떤 원본을 어떤 값으로 이전하려 했는가 |
| API 응답 | 새 결제 서버에서 어떤 결과를 돌려줬는가 |
| 주문 매핑 | 서비스 주문에 새 결제 서버의 식별정보가 반영됐는가 |

마지막 매핑 저장이 실패했다고 앞서 남긴 요청·응답까지 함께 롤백되면, 어디까지 진행됐는지 다시 조사해야 한다. 기록의 커밋 경계를 나눈 이유는 후속 작업이 실패해도 앞 단계의 확인 근거를 남기기 위해서였다.

물론 기록을 나눠 저장한다고 두 서버의 처리가 하나의 원자적 작업이 되지는 않는다. 응답 기록이 없다는 사실만으로 상대 서버의 적재 실패를 단정할 수도 없다. 이미 적재됐지만 응답이 도착하지 않았거나, 응답을 저장하는 데 실패했을 수 있다.

따라서 별도 기록과 멱등 API가 함께 필요했다. 기록으로 확인할 수 있는 상태를 좁히고, 재요청이 필요할 때는 같은 식별키로 처리해 중복 적재를 방지했다. 실패하거나 부분 완료된 건은 수동으로 확인했고, 대상 ID 목록을 지정해 재실행할 수 있는 경로를 마련했다.

자동 복구까지 구현한 구조는 아니었다. 다만 전체 배치를 처음부터 반복하거나, 성공 여부를 추측해서 데이터를 수정하는 대신 확인이 필요한 대상을 골라 재처리할 수 있었다.

## 전환 중에는 결제를 막고, 권한 만료를 늦췄다

전환 시점에는 과거 데이터의 정합성 외에 사용자의 이용 권한도 고려해야 했다. 결제 이벤트 처리가 지연되는 동안 구독 권한이 먼저 만료되면, 갱신 대상 사용자가 서비스를 이용하지 못할 수 있었다.

배포 시작부터 예상 종료 시점에 버퍼를 더한 시간까지를 전환 구간으로 잡았다. 이 구간에 갱신될 구독은 권한 만료를 전환 종료 예정 시점까지 미뤘다. 신규 결제는 잠시 차단하고, 이전이 끝난 뒤 지연된 이벤트를 소급 처리했다.

즉시 처리할 수 없는 이벤트들의 영향은 같지 않았다. 갱신은 권한 공백을 막는 조치가 먼저 필요했고, 환불과 구독 취소는 이번 전환 구간 동안 처리를 지연한 뒤 소급 반영하는 방식으로 진행했다.

결제와 구독 갱신 처리가 지연될 수 있다는 점, 그동안 이용 권한의 공백은 발생하지 않도록 한다는 점도 미리 공지했다. 결제를 잠시 제한하는 대신 기존 사용자의 서비스 이용을 보호하도록 전환 절차를 구성했다.

## 하나의 구독 키를 확정할 수 없었던 19건

App Store 구독 19건은 기존 기록만으로 구독 키를 하나로 확정할 수 없었다. 키 후보가 전혀 없는 경우만을 뜻하는 것은 아니었다. 후보가 두세 개이거나, 최초 거래를 판별하기 어려워 구독을 식별할 값을 결정하지 못한 경우였다.

후보 중 하나를 임의로 확정하면 이후 갱신 이벤트를 잘못 연결할 수 있었다. 이 건들은 임시키로 이전하고, 구독을 찾지 못하는 이벤트가 발생하면 알림을 받아 확인하도록 했다. 실제 갱신 이벤트가 도착했을 때 다음 순서로 처리했다.

1. 이벤트에 담긴 구독 키와 기존 후보 기록을 수동으로 대조한다.
2. 해당 구독의 식별키를 확정한다.
3. 이전된 결제 내역을 확정한 구독 키로 보정한다.
4. 연결하지 못했던 이벤트를 재시도해 처리한다.

최종적으로 19건 모두 다음 결제 갱신 시점에 보정을 마쳤다. 갱신 시점까지 추적하고 사람이 확인해야 하므로 대규모 예외에 그대로 적용할 방법은 아니었다. 다만 확정할 수 없는 19건에 대해서는 잘못된 연결을 만들어두는 대신, 실제 이벤트에서 근거를 확보할 때까지 후속 처리를 이어갔다.

이 사례에서는 적재 성공과 문제 해결의 시점이 달랐다. **임시키가 들어간 순간이 아니라, 다음 갱신에서 연결을 보정한 순간까지가 작업 범위였다.**

## 무엇을 확인해야 완료라고 할 수 있을까

최종적으로 전체 데이터 이전을 진행했고, 실제 적재는 약 80만~90만 건의 API 요청 규모였다. 하지만 요청 수만으로 정합성을 판단하지는 않았다. 확인하려는 대상에 따라 검증 방법을 나눴다.

| 확인 대상 | 검증 방법 |
| --- | --- |
| 결제·환불 내역의 누락과 중복 | 결제 서버 측에서 이전 건수와 선정한 멱등성 키를 기준으로 확인 |
| 당해 연도 재무 데이터 | 두 서버에서 정산을 수행해 결제·환불 금액 집계를 대조 |
| 이후 결제 이벤트 처리 | 결제 서버와 서비스 양쪽의 처리 실패를 알림으로 모아 모니터링 |

각 방법이 확인해주는 범위도 달랐다. 건수가 맞아도 서로 다른 누락과 중복이 상쇄될 수 있고, 합계가 맞아도 개별 기록이 모두 같다는 뜻은 아니다. 특히 금액 대조는 당해 연도 데이터를 대상으로 했으므로 전체 과거 데이터까지 같은 수준으로 검증했다고 말할 수는 없다.

이전 이후에는 결제 처리 실패를 모으는 Slack 알림 채널을 추가해 두 서버를 함께 확인했다. 갱신·취소·만료·환불 이벤트가 기존 구독과 주문에 연결되고, 서비스 이용 권한의 갱신이나 만료까지 이어지는지 살폈다.

## 오류를 줄이자 남은 오류도 보이기 시작했다

중복 구독을 만드는 경로를 수정한 뒤 중복 구독을 가진 사용자가 줄었다. 두 구독이 각각 갱신되면서 이미 이용 권한이 있는 사용자에게 다시 권한을 부여하려던 오류도 더 이상 관찰되지 않았다.

변화는 해당 오류의 감소에 그치지 않았다. 기존에는 많은 오류와 false positive가 섞여 개별 실패를 제대로 살피기 어려웠다. 반복되던 오류를 줄이자 남은 알림을 확인할 수 있었고, 정상 처리를 실패로 잡던 false positive도 순차적으로 정리할 수 있었다. 이후에는 들어오는 결제 실패를 하나씩 확인할 수 있는 수준으로 모니터링이 개선됐다.

중복 구독의 원인 수정과 이후의 오류·알림 정리를 포함한 일련의 개선으로, 결제 처리 오류율은 80% 이상 낮아졌다. 이는 여러 후속 개선을 합친 결과다.

이번 작업은 과거 데이터를 설명할 수 있는 상태로 복원하는 데서 시작했다. 그 과정에서 현재도 중복 구독을 만드는 로직을 발견했고, 이전 이후에도 남은 이벤트와 오류를 추적하며 수정했다. **다음 결제가 기존 구독과 주문으로 이어지는지 확인하는 일이, 기존 결제 흐름을 개선하는 계기가 됐다.**
